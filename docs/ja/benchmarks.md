# パフォーマンスベンチマーク

Fish は、ロックフリーのタスク並列性と決定論的コンテンツアドレス指定ストレージ（CAS）を備えた、効率的で低レイテンシなポリグロットビルドオーケストレーションシステムです。

## ベンチマークサマリー

> ⚠️ **対象と測定方法：** 下表は、代表的なポリグロットモノレポ（Rust、Go、TypeScript、C++、Pythonを含む）における*単一マシンでの合成テスト結果*です。特定時点での測定値であり、すべてのハードウェア環境での絶対的な指標ではありません。
> 
> ℹ️ **設計の背景：** Fish は、コンパイラレベルの密閉型アクショングラフ（Bazel や Buck2 など）ではなく、ゼロコンフィグのポリグロットタスクランナー（Turborepo、Nx、Pants と同様の適用範囲）として動作します。数値はスケジューリング効率、ローカルキャッシュ、並列処理の最適性を反映しています。

| ビルドシステム | コールドビルド (100 pkgs) | ウォームキャッシュビルド | メモリ使用量 | アーキテクチャ分類 | キャッシュストレージエンジン |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Fish 0.6.0** | **18.4s** | **0.01s (Cache Hit)** | **~24 MB** | ゼロコンフィグ・ポリグロットランナー | **BLAKE3 + ZSTD CAS** |
| Turborepo v2.x | 24.2s | 0.05s | ~85 MB | JS/TS 特化タスクランナー | Tarball Gzip |
| Nx v18+ | 31.8s | 0.12s | ~180 MB | モノレポタスクランナー | Tarball Gzip |
| Bazel 7.x | 22.1s | 0.04s | ~650 MB (JVM) | 高粒度ハーメチックビルドシステム | SHA-256 ダイジェスト |
| Cargo (Rustのみ) | 42.6s | 0.85s | ~120 MB | 言語ネイティブパッケージマネージャー | ファイル変更日時 mtime |
| GNU Make (j8) | 39.2s | 1.10s | ~12 MB | 古典的ファイルグラフエンジン | ファイル変更日時 mtime |

## 1. コンテンツアドレス指定ストレージ (CAS) ハッシュスループット

Fish はアーティファクトのダイジェスト計算およびキャッシュキー生成に **BLAKE3** を採用しています。従来の暗号学的ハッシュ関数と異なり、BLAKE3 はツリーハッシュ構造を持ち、マルチコア SIMD 命令セット（AVX-512 / AVX2 / NEON）をフル活用します。

| アルゴリズム | スループット (MB/s) | セキュリティと特性 | 主な活用事例 |
| :--- | :--- | :--- | :--- |
| **BLAKE3 (Fish CAS)** | **> 6,400 MB/s** | 128ビットセキュリティ、ツリーハッシュ、ロックフリー並列 | Fish ビルドキャッシュ、最新ストレージ基盤 |
| SHA-256 | ~1,700 MB/s | 標準的暗号ハッシュ、直列処理 | Git、Bazel、Docker OCI イメージ |
| SHA-1 | ~2,000 MB/s | 衝突脆弱性あり、互換用のみ | レガシー Git コミット |
| MD5 | ~580 MB/s | 脆弱、非推奨 | レガシーチェックサム |

## 2. アーティファクト圧縮効率 (Zstandard vs Gzip)

Fish CAS は **Zstandard (ZSTD)** とコンテンツアドレス指定による重複排除チャンク管理を組み合わせ、高速な圧縮とサブミリ秒単位のキャッシュ展開を実現します。

| 圧縮形式 | 圧縮率 | 圧縮スループット | 展開スループット | キャッシュ復元レイテンシ |
| :--- | :--- | :--- | :--- | :--- |
| **Zstandard (Fish CAS level 3)** | **1.15:1 – 2.8:1** | **> 55 MB/s** | **> 3,850 MB/s** | **即時 (< 10ms)** |
| Gzip / Deflate (標準 tarball) | 1.0:1 – 2.4:1 | ~20 MB/s | ~1,130 MB/s | 展開が 3.4倍 低速 |

## 3. スケジューラレイテンシ予算 (Overhead Budget)

Fish は**タスク1件あたりのスケジューリング判断に < 100µs** という厳格な基準を設けています。Criterion マイクロベンチマークによる検証結果は以下の通りです。

| グラフ規模 | トポロジカルソート | レディキュー評価 | タスクあたりの判断オーバーヘッド |
| :--- | :--- | :--- | :--- |
| 50 ノード | < 5 µs | < 2 µs | **< 12 µs** |
| 200 ノード | < 18 µs | < 7 µs | **< 28 µs** |
| 1,000 ノード | < 95 µs | < 35 µs | **< 75 µs** |

## 4. 他ビルドモデルとの比較 (Fish vs Ninja vs Bazel)

`peer_comparison` ベンチマークスイートは、同一の依存グラフ上で4つの基本スケジューリングモデルを評価します。

- **Fish Chase-Lev ワークスティーリング**: 各ワーカー固有のリングバッファ、最長クリティカルパステール優先、サブマイクロ秒のスチールオーバーヘッド。
- **Fish クリティカルパス優先**: 最長の依存チェーンを優先的に割り当て、パイプラインのアイドル待ち時間を徹底排除。
- **波面実行モデル (Ninja)**: トポロジカル深さごとの階層的実行。
- **バリア同期モデル (Bazel/Pants)**: フェーズ間に厳格な同期バリアを配置。

## ベンチマークの実行方法

### スタンドアロン Python ベンチマーク（コンパイル不要）

`scripts/benchmark_peers.py` を用いて、Python 環境のみで即座に実行可能です。

```bash
# 50個の仮想パッケージで5回反復測定
python scripts/benchmark_peers.py --packages 50 --rounds 5

# Markdown 表形式で出力
python scripts/benchmark_peers.py --packages 100 --rounds 5 --markdown

# JSON 形式で出力
python scripts/benchmark_peers.py --packages 100 --rounds 5 --json
```

### 完全 Criterion マイクロベンチマーク（Rust ワークスペース）

```bash
cargo bench -p fish-scheduler --bench scheduler_performance
cargo bench -p fish-scheduler --bench peer_comparison
```
