# 比較マトリクス: Fish と他のビルドシステム

Fish は、Rust 2024 で構築された、最新のポリグロットモノレポ（Polyglot Monorepo）向けビルドオーケストレーションシステムです。Bazel、Turborepo、Buck2 との客観的な技術比較は以下の通りです。

| 機能 / 次元 | Fish | Turborepo | Bazel | Buck2 |
| :--- | :--- | :--- | :--- | :--- |
| **開発言語** | Rust 2024 | Go / Rust | Java / C++ | Rust |
| **言語サポート** | ネイティブポリグロット (11+ ツールチェーン) | JS / TS 特化 | ポリグロット (Starlark ルール) | ポリグロット (Starlark ルール) |
| **構成モデル** | `fish.toml` / 自動検出 | `turbo.json` | `WORKSPACE` + `BUILD.bazel` | `BUCK` ルール定義 |
| **設定の複雑さ** | ゼロコンフィグ / 最小限 | 低 | 高 (目標ごとの厳密な定義が必要) | 高 (目標ごとの厳密な定義が必要) |
| **ハッシュエンジン** | Blake3 (並列ツリーハッシュ) | SHA-256 | SHA-256 | Blake3 / SHA-256 |
| **CAS 圧縮形式** | Zstandard (Zstd) + CoW | Tar.gz / Gzip | Zstd / カスタム | Zstd / カスタム |
| **ローカル展開** | Reflink / CoW (コピーへフォールバック) | ファイル全体コピー | シンボリックリンク / ハードリンク | Reflink / CoW |
| **データ重複排除** | FastCDC (16KB - 256KB チャンク) | アーカイブ全体 | アーカイブ全体 | チャンク化 CAS |
| **仮想ファイルシステム** | メモリスナップショットツリー | ディスク走査 | Inotify / Watchman デーモン | Watchman / EdenFS |
| **セマンティック無効化**| AST インターフェースハッシュ (ABI 単位) | ファイルハッシュのみ | ヘッダーのみのコンパイル | ヘッダー / rmeta 単位 |
| **AI 診断・修復** | ネイティブ IPC + 原因究明支援 | なし | なし | なし |
| **ダッシュボード** | 組み込み Web GUI + TUI | Vercel Web アプリ | サードパーティ製 UI | オープンソースコンソール |

## アーキテクチャの詳細分析

### Fish vs Turborepo
* **適用言語の範囲:** Turborepo は主に JavaScript/TypeScript モノレポ向けに設計されています。Fish は Cargo、Go modules、CMake、Python、Docker など 11 種類以上のツールチェーンをネイティブマニフェストから直接自動認識して並列実行します。
* **ストレージと I/O 効率:** Turborepo は一般的な tarball 圧縮を採用しています。Fish は Reflink CoW と FastCDC チャンク重複排除を駆使し、無駄なディスク I/O や帯域消費を極小化します。

### Fish vs Bazel
* **設計思想とトレードオフ:** Bazel は厳格な密閉型サンドボックス（Hermetic Sandbox）を必要とする超大規模組織向けに作られており、すべてのターゲットに `BUILD.bazel` を記述する必要があります。Fish はゼロコンフィグの軽量タスクオーケストレーターとして設計されており、迅速な導入と低リソース消費を最優先しています（Fish の RAM 消費は約 24 MB、Bazel JVM は 650 MB 以上）。
* **実行基盤アーキテクチャ:** Bazel は重量級の JVM デーモンに依存します。Fish は自己完結型のネイティブ Rust バイナリとして動作し、起動遅延は 15ms 未満です。

### Fish vs Buck2
* **ワークフローと保守性:** Buck2 は Starlark ルールを使用する高性能ビルドシステムです。Fish はインメモリ VFS や GNU jobserver プールを組み込み済みで提供し、設定ファイルのメンテナンス負荷をゼロに抑えることを目指しています。

## 実証ケーススタディ: Bazel vs Fish（`bazelbuild/examples` による検証）

> ⚠️ **免責事項 —— 参考情報としての提供:**
> 本ケーススタディにおける実測値は、一般的な Windows x86_64 開発環境（4 CPU コア、約 3.8 GB RAM）上で、Google 公式サンプルリポジトリ [`bazelbuild/examples`](https://github.com/bazelbuild/examples)（コミット `3c479f4`）を対象に測定されたものです。
> **これらの測定結果は、アーキテクチャ上の設計思想の違いを理解するための参考情報として提示されています。** 実際のプロダクション環境における性能は、ハードウェア構成、SSD I/O 性能、ネットワーク帯域（リモートツールチェーン取得時）、キャッシュ状態によって変動します。Bazel は初期コストと引き換えにコンパイラレベルの密閉環境を提供し、Fish はゼロコンフィグによる開発者の即応性と超低レイテンシ実行を重視しています。

### 検証環境と測定手順

`bazelbuild/examples` 内の Go 言語チュートリアル全3ステージ（`stage1`, `stage2`, `stage3`）を対象に検証を実施しました。
- **キャッシュ完全クリア手順:**
  - **Bazel:** `bazel clean --expunge` を実行して出力キャッシュとサンドボックスを完全消去し、JVM サーバープロセスを停止。
  - **Fish:** `.fish/cache` ディレクトリおよびローカル生成物（`build/`）を完全消去。
- **対象タスク:** テストを実行しない純粋なバイナリ生成ビルド（Bazel は `go_binary`、Fish はテスト無効化設定の `go build`）。

### 実測ベンチマーク結果

| 検証対象モジュール | ターゲット名 | Bazel 7.4.0 (コールドビルド) | Bazel 7.4.0 (ウォームキャッシュ) | Fish 0.6.0 (コールドビルド) | Fish 0.6.0 (ウォームキャッシュ) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Go Tutorial Stage 1** | `hello` | 165.53s | 23.55s | **1.08s** | **0.00092s (0.9ms)** |
| **Go Tutorial Stage 2** | `print_fortune` | 145.89s | 23.40s | **1.69s** | **0.00095s (0.9ms)** |
| **Go Tutorial Stage 3** | `fortune_test` | 149.68s | 23.70s | **0.99s** | **0.00088s (0.8ms)** |
| **3プロジェクト合計** | **全3ターゲット** | **461.10s (~7.7 分)** | **~70.65s** | **3.76s** | **0.00275s (2.7ms)** |

### アーキテクチャ要因の分析

1. **コールドビルド所要時間の差異 (461.10s vs 3.76s):**
   - **Bazel:** JVM を起動し、Bazel 7.4 リリースと `rules_go` を取得、101 個のパッケージと 10,800 個以上のターゲットを評価、サンドボックス内で `builder.exe` 補助ツールと Go 標準ライブラリ全体をコンパイルする必要があります。
   - **Fish:** ローカルマシンに既に存在する Go ツールチェーンを即座に認識し（起動時間 < 15ms）、不要なダウンロードを回避して分散ワークスティーリングキューに直ちにタスクを投入します。

2. **ウォームキャッシュ所要時間の差異 (~70.65s vs 0.00275s):**
   - **Bazel:** ソースコードに変更がない場合でも、JVM デーモンへの接続、Starlark グラフの再評価、数千のターゲットハッシュの照合処理が発生します。
   - **Fish:** BLAKE3 ツリーハッシュにより、マイクロ秒単位でメタデータとコンテンツフィンガープリントを高速判定します。変更がないことを瞬時に検知し、**100% キャッシュヒット**を達成、全3プロジェクトの検査が 3ミリ秒未満 で完了します。
